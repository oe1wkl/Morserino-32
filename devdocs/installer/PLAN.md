# Unified Web Installer — Design & Migration Plan

Status: **draft for review** (2026-08-05). No code written yet.
Branch when work starts: **`unified-installer`** (off `master`, per CLAUDE.md §1).

---

## 1. Goal

Replace the two hand-maintained, platform-specific web installers with **one page**
that:

1. **Identifies the board itself** by querying the connected processor
   (ESP32 → classic M32, ESP32-S3 → M32 Pocket) instead of asking the user to
   pick the right page.
2. Lets a Pocket owner choose the **edition** — Standard or Accessibility — since
   both run on the same chip and cannot be told apart by detection.
3. Flashes the **filesystem image** that the Accessibility Edition needs, not just
   the application binary.
4. Has its source **in this repository**, reviewable and diffable, instead of
   living only inside the Sitely website project in two copy-pasted variants.

Non-goals: the standalone desktop updater (`Morserino-32-Firmware-Updater/m32update`),
the config tool and file manager, and OTA/WiFi updating. Those stay as they are.

## 2. Where things stand today

### 2.1 The two installers

| | Classic | Pocket |
|---|---|---|
| Page | `www.morserino.info/flash.html` | `.../flash-m32pocket.html` |
| Registry | `firmware/versions.json` | `firmware/m32p/versions.json` |
| Binaries | `firmware/` | `firmware/m32p/` |
| Shared parts | `firmware/common/` | `firmware/m32p/common/` |
| Bootloader offset | `0x1000` | `0x0000` |
| `chipFamily` | `ESP32` | `ESP32-S3` |

Both pages are generated by **Sitely 6.2.1** from `~/Documents/Sparkle/New/m32.sparkle`
and embed an inline `<script>` that fetches `versions.json`, builds an
[ESP Web Tools](https://esphome.github.io/esp-web-tools/) manifest as a `blob:` URL, and
hands it to `<esp-web-install-button>` (loaded live from `unpkg.com/esp-web-tools@10`).

**The two scripts are byte-identical apart from the five constants in the table above.**
Everything else — version dropdown, beta toggle, badges, error handling — is duplicated.
Neither copy is in git; the source of truth is a code block inside the Sitely project,
so the installer is un-reviewable, un-diffable, and must be edited twice.

### 2.2 Publishing chain

`.github/workflows/release.yml` (self-hosted macOS runner)
→ `scripts/release/rename_binaries.py` (stages `<env>/firmware.bin` under the release
filename; `PLATFORMS` has exactly two entries)
→ `scripts/release/dropbox_publish.sh` (copies into
`~/Library/CloudStorage/Dropbox/Apps/site44/www.morserino.info/firmware/…`)
→ `scripts/release/update_manifest.py` (prepends an entry to that platform's
`versions.json`).

`versions.json` entry schema today:

```json
{ "version": "8.2", "filename": "fw_m32_V8.2.bin", "notes": "Release of V.8.2", "beta": false }
```

Dropbox syncs to site44, which serves `www.morserino.info`. Hand-placed files survive
Sitely publishes — `m32_config_tool.html` has lived at the site root for months and is
linked from the Sitely-built `index.html`. That is the precedent this plan relies on.

### 2.3 What V9 adds

A third artifact set from `env:pocketwroom-accessibility`:

| Artifact | Size (current build) | Notes |
|---|---|---|
| `firmware.bin` | 2,193,232 B | must stay < `0x2D0000` (2,949,120 B) |
| `partitions.bin` | 3,072 B | **differs** from the mainline Pocket table |
| `spiffs.bin` | 5,308,416 B | 478 voice clips, 4.1 MB of MP3 |

Partition tables (`m32pocket_accessibility.csv` vs the board default `default_8MB.csv`):

| | nvs | otadata | app0 | app1 | spiffs |
|---|---|---|---|---|---|
| Pocket standard | `0x9000`/`0x5000` | `0xE000` | `0x10000`/`0x330000` | `0x340000`/`0x330000` | `0x670000`/`0x180000` |
| Pocket a11y | `0x9000`/`0x5000` | `0xE000` | `0x10000`/`0x2D0000` | — | `0x2E0000`/`0x510000` |

Three consequences that drive the design:

- **NVS is at the same offset and size in both** → all preferences, snapshots and
  high scores survive an edition switch, *provided the installer does not erase the
  whole flash*.
- **The a11y table has no `ota_1`.** A leftover `otadata` selecting slot 1 would brick
  the boot. Writing `boot_app0.bin` at `0xE000` (all-`0xFF`, i.e. "no OTA selection")
  resets it — the current `SHARED_PARTS` list already does this, and it must stay.
- **SPIFFS moves and changes size.** Switching editions loses the file-player content
  (`player.txt`). Going a11y → standard leaves stale voice data at the new SPIFFS
  offset; the firmware mounts with `SPIFFS.begin(FORMAT_SPIFFS_IF_FAILED)`
  ([m32_v6.ino:814](Software/src/Version%206%20and%20newer/m32_v6.ino:814)), so it
  self-heals by reformatting. Verify on hardware, don't assume.

Both Pocket editions are **ESP32-S3**, so chip detection alone cannot choose between
them — hence the explicit edition selector.

## 3. Decisions taken (2026-08-05)

| Decision | Choice | Rationale |
|---|---|---|
| Flashing engine | **Own flasher on `esptool-js`** | One port prompt; the page can *show* what it found before flashing; full control over the 5.3 MB filesystem write and its progress; a page whose accessibility we own — which matters because the Accessibility Edition's own users have to operate it. |
| Source location | **Self-contained HTML in this repo**, published to the site | Ends the two-copies-in-Sitely situation; matches the `m32_config_tool.html` convention. |
| Old URLs | **Redirect** `flash.html` and `flash-m32pocket.html` to the new page | Bookmarks, forum posts and manual links keep working; exactly one installer to maintain from day one. |
| Accessibility Edition | **A normal, visible edition choice** on the public installer | Not hidden, not on request — it sits next to Standard for every Pocket owner. |
| Installed-version probe | **Yes, best effort**, with a grace exit for firmware that cannot answer | Useful ("you have V8.2, latest is V9.0") but must never block or fail the install — see §4.3. |

The rejected alternative was keeping ESP Web Tools with a two-build manifest (it would
auto-select by chip family for free, ~1–2 days instead of ~4). It was rejected because
it cannot show the detected board before flashing and its dialog is not ours to make
accessible. **The cost of that choice is that we now own the reset/timing behaviour
esp-web-tools handles today — see §9.1.**

## 4. Target design

### 4.1 User flow

```
  ┌── 1. Connect ────────────────────────────────────────────┐
  │  "Plug in your Morserino and press Connect."             │
  │  → navigator.serial.requestPort()  (one prompt, ever)    │
  └──────────────────────────────────────────────────────────┘
                            ↓
  ┌── 2. Identify & choose ──────────────────────────────────┐
  │  "Found: M32 Pocket (ESP32-S3, 8 MB flash)"              │
  │  "Installed: V8.2 (build Jun 22 2026)"   ← best effort   │
  │  Edition:  (•) Standard   ( ) Accessibility Edition      │
  │  Version:  [ V9.0  ← latest      ▾ ]   [ ] show betas    │
  │  Settings: (•) Keep my settings  ( ) Erase everything    │
  └──────────────────────────────────────────────────────────┘
                            ↓
  ┌── 3. Flash ──────────────────────────────────────────────┐
  │  Downloading  ████████░░  4.1 / 7.4 MB                   │
  │  Writing      ██████░░░░  62 %   (voice clips)           │
  │  → "Done. Unplug and switch your Morserino on."          │
  └──────────────────────────────────────────────────────────┘
```

For a classic M32 step 2 shows no edition control at all — there is only one target
for `ESP32`. Nothing about "Pocket" is ever shown to a classic owner and vice versa.

### 4.2 Board identification

```js
const port      = await navigator.serial.requestPort();
const transport = new Transport(port, true);
const loader    = new ESPLoader({ transport, baudrate: 921600, romBaudrate: 115200, terminal });
await loader.main();                 // syncs, detects
loader.chip.CHIP_NAME                // "ESP32" | "ESP32-S3"
```

Selection rule — **data-driven, no board names in code**: filter the target list by
`chipFamily === detected`. One match → use it silently. More than one → render them as
the edition choice. A future variant is then a registry entry, not a code change.

Guard rails:

- **Unknown chip** (`ESP32-C3`, `ESP8266`, …) → "This does not look like a Morserino",
  no install offered.
- **Other S3-based M32 builds exist** (`heltec_wifi_kit_32_V3`, `heltec-vision-master-t190`,
  `minipcb_lora`) and would be detected as "Pocket". They are not published targets, so
  the risk is theoretical, but the page gets an **"Other hardware / flash a local file"**
  escape hatch: pick any published artifact explicitly, or a `.bin` from disk — also the
  path beta testers and the maintainer need.
- **Flash size cross-check** — refuse to flash the a11y image on < 8 MB flash.

### 4.3 Identifying the installed firmware (best effort)

Before anything touches the reset lines, the page asks the *running* firmware who it is,
using the M32 serial protocol at 115200 baud:

```
→  PUT device/protocol/on
←  {"device":{"hardware":"M32 2nd edition","firmware":"8.2","protocol":"1.3","build":"Jun 22 2026"}}
```

The handshake is ungated in the firmware — `m32_v6.ino` accepts it whenever
`serialEvent()` is polled, regardless of the *Serial Output* preference — so it works on
any reasonably recent device. It yields more than the version: `hardware` is the
build's `HW_NAME`, an independent second opinion on which board this is.

**The grace exit is the whole design.** All of these are normal, not errors: firmware
older than the protocol, a device busy in a mode that is not polling serial, a sleeping
device, a blank board, a non-JSON or malformed reply, a reply without a `device` object,
a port error. Every one of them produces the same outcome:

- the line reads "Installed version: unknown";
- **no error, no warning, no interruption** — the flow is identical either way;
- the probe is asynchronous with a ~1.5 s timeout and runs while the user is reading
  step 2, so it never adds latency to the flow. It fills the line in when it arrives.

Two details not to miss:

- `hardware` vs. the detected chip family: if they disagree, **the chip wins** for
  choosing what to flash (it is the thing being written to), but show both — a
  disagreement means either an unusual build or a bug worth hearing about.
- Enabling the protocol suppresses the device's sleep timeout, but no goodbye is needed:
  every path out of the probe ends in a chip reset (connecting resets into the
  bootloader, cancelling and finishing both hard-reset), and `m32protocol` is a RAM flag
  that does not survive one.

The probe closes the port before `esptool-js` opens it again — the two never share it.

*As built:* worst case (a device that never answers) is 3.4 s, and a device that does
answer replies in well under 100 ms. The status line reads "Checking the device…"
throughout, so the slow case is never a blank wait.

### 4.4 Flash plan per target

| Target | Chip | Parts (offset → file) |
|---|---|---|
| `m32` | ESP32 | `0x1000` bootloader · `0x8000` partitions · `0xE000` boot_app0 · `0x10000` app |
| `m32p` | ESP32-S3 | `0x0000` bootloader · `0x8000` partitions · `0xE000` boot_app0 · `0x10000` app |
| `m32p-a11y` | ESP32-S3 | `0x0000` bootloader · `0x8000` partitions · `0xE000` boot_app0 · `0x10000` app · **`0x2E0000` filesystem** |

Written with `compress: true`; `eraseAll` only when the user asks for it (§4.5).

**Restarting afterwards — a real trap.** `esptool-js`'s `after('hard_reset')` does *not*
reset anything on its own: `HardReset.reset()` only ever calls `setRTS(false)`, i.e. it
**releases** a line it assumes is already asserted. Call it by itself and nothing happens
— the device sits in the bootloader until the user power-cycles it by hand. The line must
be pulled low first:

```js
await transport.setRTS(true);   // EN low — chip held in reset
await sleep(100);
await loader.after('hard_reset');   // chip-specific release
```

This is exactly what esp-web-tools does (`hardResetDevice()` in its `flash.ts`), which is
why the old installers rebooted the device and the first version of this one did not.

### 4.5 Data-preservation rules

Two explicit choices, defaults chosen so the safe thing happens by accident:

- **Keep my settings (default)** — `eraseAll: false`. NVS survives, so preferences,
  snapshots and high scores survive, including across an edition switch. The parts
  above still rewrite the partition table and reset the OTA selector, which is exactly
  what an edition switch needs.
- **Erase everything** — `eraseFlash()` first. The page must say, in words, that this
  wipes preferences, snapshots, high scores and any player text.

When the selected edition differs from what the flash geometry suggests is installed,
warn that the file-player text will be lost (SPIFFS moves).

### 4.6 Visual design

The page **reuses the visual language of the pages it replaces** — same Lato faces from
`css/`, the same tokens (`--accent #cb4b16`, `--box-bg #ddedf7`, `--box-border #677a85`,
the 8/10/4 drop shadow, 7 px radius), the same bordered boxes, numbered step circles,
uppercase field labels, custom-styled select and checkboxes, the beta/latest/older badge
family, the version-info strip, and the animated Morse "M32" header. Someone arriving
from morserino.info should not notice they have left it.

What marks it as new: a **`new` badge** beside the title in the accent colour (same badge
family as `latest`/`beta`) and the subtitle *"One installer for every Morserino — it
recognises which one you plugged in."* The step-per-card layout is itself new; the old
pages were a single card.

Two deliberate departures: custom **radio** styling had to be invented (the old pages had
no radios), and the page is **light-only**, matching the site, rather than following the
system dark preference. The Morse header respects `prefers-reduced-motion`.

### 4.7 Accessibility of the installer itself

Not optional here: the Accessibility Edition's first install is done by, or for, a
blind operator on a device that cannot yet speak. Requirements:

- Semantic HTML, real `<button>`/`<select>`/`<fieldset>`, every control labelled.
- Full keyboard operation; visible focus; focus moves to the new step's heading.
- Progress and completion announced via `aria-live="polite"`; errors via `role="alert"`.
- Never colour-only status; text always says what colour would.
- Screen-reader pass with VoiceOver/Chrome before release.

Page language stays **English**, consistent with the device UI (CLAUDE.md §5).

## 5. Server-side layout and registry schema

Keep every existing `versions.json` exactly as it is — the release scripts write them
and the old pages read them during the transition — and add **one new static file** on
top that describes the targets:

```
firmware/
  targets.json            ← NEW: what targets exist, their chip, parts and offsets
  versions.json           ← unchanged (classic)
  common/…                ← unchanged
  m32p/
    versions.json         ← unchanged
    common/…
  m32p-a11y/              ← NEW
    versions.json
    common/{bootloader,partitions,boot_app0}.bin   ← a11y table, from its own build
    fw_m32pa11y_V9.0.bin
    fs_m32pa11y_V9.0.bin
```

`targets.json` — as built, in `Software/Utilities/targets.json`; paths are relative to
the registry's own location, so it carries no absolute URLs:

```json
{
  "schema": 1,
  "targets": [
    { "id": "m32", "hardware": "Morserino-32 (1st / 2nd edition)", "label": "Standard",
      "chipFamily": "ESP32", "dir": "", "versions": "versions.json",
      "parts": [ { "path": "common/bootloader.bin", "offset": 4096,  "label": "bootloader" },
                 { "path": "common/partitions.bin", "offset": 32768, "label": "partition table" },
                 { "path": "common/boot_app0.bin",  "offset": 57344, "label": "boot selector" } ],
      "appOffset": 65536 },

    { "id": "m32p", "hardware": "M32 Pocket", "label": "Standard",
      "chipFamily": "ESP32-S3", "dir": "m32p/", "versions": "versions.json",
      "parts": [ { "path": "common/bootloader.bin", "offset": 0, "label": "bootloader" }, … ],
      "appOffset": 65536, "minFlashMB": 8 },

    { "id": "m32p-a11y", "hardware": "M32 Pocket", "label": "Accessibility Edition",
      "chipFamily": "ESP32-S3", "dir": "m32p-a11y/", "versions": "versions.json",
      "parts": [ … ], "appOffset": 65536, "minFlashMB": 8,
      "fsOffset": 3014656, "fsLabel": "voice clips",
      "note": "Speaks the menus and settings aloud, for blind and partially sighted operators. The games are not included." }
  ]
}
```

`hardware` names the board (the "Found:" line), `label` names the edition (the radio
button); the order of the array is the order the editions are offered. The `note` says
nothing about settings surviving — whether they do depends on the erase choice, so that
sentence belongs to the live warning in the page, not to a static string.

The only change to `versions.json` is **one optional field** on entries that ship a
filesystem image:

```json
{ "version": "9.0", "filename": "fw_m32pa11y_V9.0.bin",
  "fs": "fs_m32pa11y_V9.0.bin", "notes": "…", "beta": false }
```

Filename prefixes follow the existing convention (`fw_m32`, `fw_m32p`): **`fw_m32pa11y`**
and **`fs_m32pa11y`**, so the beta-suffix logic in `rename_binaries.py` needs no new
parsing rules.

## 6. Release-pipeline changes

All four touch points are small and shaped the same way as the existing two platforms:

1. **`release.yml`** — build a third environment, and produce its filesystem image:
   ```bash
   pio run -e pocketwroom-accessibility
   pio run -e pocketwroom-accessibility -t buildfs
   ```
   Add a guard that `firmware.bin` < `0x2D0000`; the a11y app partition is 0.5 MB
   tighter than the mainline one and nothing else would catch an overflow.

2. **`rename_binaries.py`** — third `PLATFORMS` entry
   `("pocketwroom-accessibility", "fw_m32pa11y", "m32p-a11y")`, and it must learn to
   stage more than one artifact per platform: the app, plus (a11y only) `spiffs.bin` as
   `fs_…bin` and `partitions.bin`/`bootloader.bin` into that target's `common/`. Emit
   the extra filenames in the JSON it prints.

3. **`dropbox_publish.sh`** — copy the extra artifacts; pass `--fs-filename` through.

4. **`update_manifest.py`** — optional `--fs-filename` → writes the `"fs"` field.

Two refinements worth having:

- **Deduplicate the filesystem image.** It is 5.3 MB and changes only when clips change.
  Hash it; if it matches the previous release's image, reference the existing file
  instead of publishing a second copy.
- **Extend the in-repo archive** (`Software/binary/From Version 7 onwards/`) with an
  a11y folder for stable releases, matching what the workflow already does for the other
  two platforms.

## 7. Where the installer lives and how it gets published

- **Source:** `Software/Utilities/m32_installer.html` — one self-contained file, like
  `m32_config_tool.html`, with **`esptool-js` vendored and inlined at a pinned version**
  (currently 0.6.1, 219 KB, making the page 251 KB). No live CDN dependency: today's
  pages load `esp-web-tools` from `unpkg` at flash time, which means an upstream change
  can break flashing without a single commit on our side. Inlining also keeps the "save
  the file and use it offline" property, which the local-file escape hatch (§4.2) makes
  genuinely useful.
  **Never hand-edit the vendored block** — `vendor-esptool.py` downloads the release,
  checks it against a pinned SHA-256, rewrites its one trailing `export{…}` into a
  `window.esptoolJS` assignment (the bundle has no imports, so that single substitution
  turns the module into a plain script) and splices it between markers. Bumping the
  version is `--print-hash`, paste, re-run — then re-test on both variants, because this
  is the code that writes to people's devices.
- **Published to:** `www.morserino.info/install.html` — **no new plumbing needed.**
  `~/sync-to-dropbox.sh` already watches `Software/Utilities/` with `fswatch` and copies
  `m32_config_tool.html` + `m32_pref_help.json` into the Dropbox site folder on every
  change. Add `m32_installer.html` and `targets.json` to it and publishing is "save the
  file". Worth doing while in there: the script carries one `SRC*`/`DST*` variable pair
  per file, which does not scale past a handful — convert it to a list of
  source→destination pairs in one loop. (The script lives in the home directory, outside
  git; moving it into `scripts/` and symlinking would make it reviewable, but that is a
  separate decision.)
- **Sitely:** `index.html` gets an "Install firmware" link; `flash.html` and
  `flash-m32pocket.html` are rebuilt as short "this has moved" pages with a link and a
  `<meta http-equiv="refresh">`.
- **`targets.json`** is versioned in the repo next to the installer and copied to
  `firmware/targets.json`.

## 8. Migration plan

Each phase ends in something testable; nothing user-visible changes before Phase 4.

**Phase 1 — parity.** ✅ **done, confirmed on real hardware 2026-08-06.** New page,
`esptool-js` engine, three-step flow, targets from `targets.json`, installed-version
probe with its grace exit, `sync-to-dropbox.sh` extended.
*Done when:* a classic M32 and a standard Pocket can be flashed with any listed
version, betas included; the probe reports a version where it can and says "unknown"
without complaint where it cannot; and the old pages have not been touched.

What exists, all on branch `unified-installer`:

| File | |
|---|---|
| `Software/Utilities/m32_installer.html` | the installer, one self-contained file |
| `Software/Utilities/targets.json` | the registry (all three targets) |
| `Software/Utilities/vendor-esptool.py` | re-vendors `esptool-js`, SHA-256 pinned |
| `~/sync-to-dropbox.sh` | now a source→destination list; `install.html` + `targets.json` added |

Verified in a browser against a local copy of the live firmware tree, with the serial
layer stubbed (real `fetch`, real registry, real part assembly — only the chip is fake):
Pocket with both editions offered and the a11y install assembling all five parts at
`0x0 / 0x8000 / 0xE000 / 0x10000 / 0x2E0000` with the right sizes, 7.5 MB downloaded;
classic offering one target and no edition control; an ESP32-C3 refused with Install
disabled; a silent device reported as "unknown" after 3.4 s with no error. Two bugs were
found and fixed this way: the erase-everything warning contradicting the Accessibility
note about settings, and the "Found:" line showing the wrong board once the
other-hardware escape hatch was on.

**Hardware confirmation (Willi, 2026-08-06):** all three targets — classic M32, Pocket
Standard, Pocket Accessibility — installed quickly and cleanly from the local test site.
§9.1 is settled: `esptool-js` picked the right reset strategy for both boards unaided.
Two follow-ups came out of that session and are fixed:

1. **The device did not restart by itself**, unlike with the old installer — the
   `after('hard_reset')` trap described in §4.4. Now asserts RTS first, as esp-web-tools
   does, and the completion message says the Morserino is restarting.
2. **The page did not look like morserino.info.** Restyled onto the old pages' design
   tokens; see §4.6.

**Not yet done, and deliberately:** nothing has been published. `sync-to-dropbox.sh` was
rewritten but not run, so the live site is untouched. Phase 4 is where publishing happens.

**Still open from §10:** the erase-everything path, an interrupted flash, the local-file
escape hatch, a foreign chip, and the screen-reader pass.

**Phase 2 — Accessibility Edition.** Third target, filesystem part, flash-size guard,
data-preservation warnings, edition selector. Manual artifact upload for testing.
*Done when:* a Pocket goes Standard → a11y → Standard with preferences intact each
time, and the voice clips work after the a11y install.

**Phase 3 — pipeline.** §6 changes; dry-run a beta release end to end.
*Done when:* one tag produces all three targets, their manifests, and the archive
commits, with no hand editing.

**Phase 4 — publish & redirect.** Ship `install.html`, link it from the site, convert
the two old pages to redirects. Update EN + DE manuals and `Software/README.md`.
*Done when:* the old URLs land on the new installer and the manuals describe one
installer.

**Phase 5 — retire.** After one release cycle, delete the leftover Sitely code blocks
and stale per-page assets. Decide then whether the desktop `m32update` tool stays.

Rough effort: Phase 1 ≈ 2 days, Phase 2 ≈ 1 day, Phase 3 ≈ 1 day, Phase 4 ≈ ½ day plus
manual work; hardware testing on top.

## 9. Risks

### 9.1 Reset and connection behaviour

**Downgraded after reading the source (2026-08-06).** The worry was that dropping
esp-web-tools meant re-owning the reset dance: classic DTR/RTS for the Heltec V2's CP2102
versus the ESP32-S3's USB-Serial-JTAG sequence. It does not. `esptool-js` picks the
strategy itself, on USB product ID — `esploader.js` uses `UsbJtagSerialReset` when
`transport.getPid() === 0x1001` and `ClassicReset` (at two delays) otherwise. The Pocket's
board definition declares hwids `303A:1001`, so it takes the USB-JTAG path automatically
and the classic M32 takes the other. esp-web-tools was never doing this for us; the
library underneath both was.

What is left is ordinary and still needs hardware: confirming the auto-selection is right
on the two real boards, and that the ROM-baud → 921600 switch holds on each.
**If it does misbehave, the two-build esp-web-tools manifest from §3 remains a working
fallback** — none of the registry, layout or pipeline work depends on which engine flashes.

### 9.2 Everything else

| Risk | Mitigation |
|---|---|
| Native-USB Pocket re-enumerates after the final reset; port handle dies | Expect it; end with a plain "unplug and switch on" instruction rather than trying to reuse the port |
| 5.3 MB download on a slow line looks like a hang | Separate download and write progress, both with byte counts |
| `esptool-js` `fileArray` data format differs by version (binary string vs `Uint8Array`) | Pin the version, verify against the pinned one, note it in the file header |
| Web Serial is Chrome/Edge/Opera only | Detect `navigator.serial` and say so plainly, with a link to the desktop updater |
| Site44/Dropbox serves the 5.3 MB image slowly or with a stale cache | Version the filename (already the convention); check propagation after the first publish |
| a11y `firmware.bin` outgrows the tighter app partition | Size guard in the release workflow (§6, item 1) |
